## <img src="assets/icons/flask.svg" width="26" height="26" align="top" alt="" /> Automation, in practice

I came to product engineering through **test automation**, and it shows in how I build.

<table>
<tr><td><img src="assets/icons/cursor-click.svg" width="20" height="20" align="top" alt="" /></td><td><b>Selenium WebDriver on Java</b> — page-object suites over real browsers, driven from Maven, with explicit waits instead of <code>Thread.sleep</code> and a screenshot on every failure.</td></tr>
<tr><td><img src="assets/icons/list-checks.svg" width="20" height="20" align="top" alt="" /></td><td><b>BDD in Cucumber / Gherkin</b> — scenarios a product owner can read and a runner can execute, so the acceptance criteria <i>are</i> the regression suite.</td></tr>
<tr><td><img src="assets/icons/plugs-connected.svg" width="20" height="20" align="top" alt="" /></td><td><b>API contracts in RestAssured</b> — status, schema and payload asserted at the boundary, independent of whatever the UI is doing that week.</td></tr>
<tr><td><img src="assets/icons/door-open.svg" width="20" height="20" align="top" alt="" /></td><td><b>Fast gate, slow net.</b> pytest on every PR because it must stay under a couple of minutes; the full browser journey runs nightly against staging, where it is allowed to be slow.</td></tr>
<tr><td><img src="assets/icons/target.svg" width="20" height="20" align="top" alt="" /></td><td><b>Acceptance happens on staging.</b> Never on the developer's machine, never on production. A ticket is not done until it is proven on the environment everybody shares.</td></tr>
</table>

## <img src="assets/icons/lightbulb.svg" width="26" height="26" align="top" alt="" /> How I work

<table>
<tr><td><img src="assets/icons/note-pencil.svg" width="20" height="20" align="top" alt="" /></td><td><b>Docs ship with the change.</b> Every backend change updates the doc that describes it, in the same commit. Decisions get an ADR — <i>"Redis is optional, here is why"</i> beats rediscovering it six months later.</td></tr>
<tr><td><img src="assets/icons/stack.svg" width="20" height="20" align="top" alt="" /></td><td><b>Environments are explicit.</b> Develop, staging and production are separate databases and separate pipelines. Nothing gets verified on the box it was written on.</td></tr>
<tr><td><img src="assets/icons/magnifying-glass.svg" width="20" height="20" align="top" alt="" /></td><td><b>I audit my own work.</b> A pre-sales security review, a first-customer readiness pass, a structural audit of the app layout — each written up with findings, owners and evidence.</td></tr>
<tr><td><img src="assets/icons/gauge.svg" width="20" height="20" align="top" alt="" /></td><td><b>Measure before optimising.</b> A load test found a ~5 req/s ceiling that looked like an undersized box. It was one serializer. <b>2.5× throughput</b> after the fix.</td></tr>
<tr><td><img src="assets/icons/globe-hemisphere-west.svg" width="20" height="20" align="top" alt="" /></td><td><b>Georgian-first products.</b> Georgian and Russian localisation, local payment rails, local DNS. i18n is never a phase-two ticket.</td></tr>
<tr><td><img src="assets/icons/traffic-signal.svg" width="20" height="20" align="top" alt="" /></td><td><b>Green before merge.</b> A red suite stops the deploy. No <code>--no-verify</code>, no secrets in the diff, no "I will fix it on main".</td></tr>
</table>
